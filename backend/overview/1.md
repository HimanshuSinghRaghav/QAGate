I went through the entire brief carefully. This hackathon is actually quite well-defined once you separate the **core product**, the **AI scoring layer**, and the **demo/dashboard layer**.

The biggest mistake would be spending 6–7 hours building a beautiful dashboard while the actual **recording → transcript → checks → evidence → gate** pipeline is incomplete. The brief explicitly says that ingestion comes first and everything else depends on it. 

# 1. First understand the hackathon in one sentence

You are building a system that does this:

> **A sales call finishes → the call/lead enters your system → transcript is available → the system checks the call against the retailer's QA rules → every result has proof → the sale is automatically passed, held, or sent to a human reviewer.**

That is the product.

The final experience should make this possible:

```text
Sales Call
   ↓
Recording + Lead ID
   ↓
Transcript + timestamps
   ↓
QA Check Engine
   ├── A. Verbatim / Script
   ├── B. Factual Match
   └── C. Behaviour
   ↓
Evidence
   ├── Transcript line
   ├── Audio timestamp
   └── Check version
   ↓
Gate Decision
   ├── GREEN → Auto-submit
   ├── RED   → Hold → TL
   └── LOW CONFIDENCE → QA
```

The brief's core requirement is exactly this: all critical checks passing allows automatic submission; a critical failure holds the sale; low-confidence results go to human QA.

# 6. MODULE 3 — Check Library

This is the heart of the business rules.

The brief defines **three completely different types of checks**. 

## A. Verbatim / Script checks

These compare:

```text
Transcript
      VS
Approved script
```

Examples:

* disclaimer
* DMO/VDO
* T&Cs
* EIC

Some of these are critical.

Example:

```text
Expected:
"I am required to inform you that this call is being recorded..."

Actual:
"I need to tell you this call is recorded..."
```

Your engine needs to determine whether that satisfies the specific check.

This is where you need to understand from the mentor how strict the supplied check definitions are.

---

# 7. B. Factual Match checks

These are extremely important because they demonstrate that your system isn't merely doing "AI sentiment analysis."

You're comparing:

```text
Transcript
   +
CRM fields
   +
Retailer plan/rate card
```

Examples from the brief include:

* quoted rate
* address
* DOB
* email
* NMI/MIRN
* fuel type
* concession
* life support
* move-in date
* gift card value. 

For example:

```text
CRM:
peak_rate = 31.9c/kWh

Transcript:
"peak is 28.6 cents"

Result:
FAIL
```

That's exactly what their worked example demonstrates. 

This should preferably be **deterministic wherever possible**.

For example:

```javascript
if (spokenRate !== crmRate) {
    fail();
}
```

Don't unnecessarily use an LLM for something that can be compared directly.

That's a strong engineering choice.

---

# 8. C. Behaviour checks

These are different.

Now there's no simple CRM value to compare.

You are evaluating the transcript itself.

Examples:

* rapport
* interruptions
* dead air
* objection handling

These are explicitly described as non-critical in the brief's table. 

This is a place where an LLM/classifier makes much more sense.

For example:

```text
Transcript
   ↓
LLM
   ↓
Behaviour analysis
   ↓
{
  dead_air: 47,
  interruptions: 3,
  objection_handling: "pass"
}
```

But don't let an uncertain behavioural result accidentally block a sale.

That's exactly why the brief distinguishes critical checks from non-critical behaviour checks.

---

# 9. The BEST architecture: Hybrid AI + deterministic rules

This is probably the most important technical recommendation I would make.

Do **not** make the whole system:

```text
Transcript → GPT → "PASS"
```

That will be hard to trust and hard to explain.

Instead:

```text
                       ┌→ Deterministic rules
Transcript ────────────┼→ Factual comparison
                       │
                       └→ LLM / semantic model
                              ↓
                         Behaviour / ambiguity
```

### For example

| Check              | Preferred method                |
| ------------------ | ------------------------------- |
| Exact disclaimer   | deterministic/fuzzy text match  |
| Account holder     | rule + entity extraction        |
| Email              | extraction + comparison         |
| Rate               | numeric extraction + comparison |
| Address            | entity comparison               |
| Dead air           | timestamps                      |
| Interruptions      | speaker/timestamp analysis      |
| Objection handling | LLM/classifier                  |
| Ambiguous phrase   | LLM + low confidence            |

This gives you a much stronger explanation when a mentor asks:

> "Why did you use AI here?"

Your answer:

> "We deliberately don't use an LLM for deterministic checks. We use structured comparisons wherever possible and reserve semantic reasoning for cases such as behaviour or ambiguous speech."

That is a very solid engineering answer.

# 10. Every check MUST return evidence

This is where many teams will probably lose points.

The brief says every score should resolve to:

1. transcript line
2. audio timestamp
3. exact check version active on the call date. 

So your result should look conceptually like:

```json
{
  "checkId": "rates_and_charges",
  "status": "FAIL",
  "critical": true,
  "confidence": 0.98,

  "expected": {
    "peakRate": 31.9
  },

  "observed": {
    "peakRate": 28.6
  },

  "evidence": {
    "transcript": "peak is 28.6 cents",
    "timestamp": "14:02",
    "segmentId": "seg_94"
  },

  "checkVersion": "v3"
}
```

Then the UI can display:

> ❌ Rates and Charges — Critical
> Agent said: **28.6 cents**
> Expected: **31.9 cents/kWh**
> Evidence: **14:02**

That directly resembles the brief's worked example.

# 11. MODULE 4 — Scoring Engine

This is your core service.

You can build something like:

```text
runScoring(leadId)
```

Which performs:

```text
1. Load lead
2. Load transcript
3. Load retailer
4. Load applicable check-library version
5. Run every check
6. Save each result
7. Calculate confidence
8. Calculate overall score
9. Apply gate
10. Create audit event
```

Pseudo-flow:

```text
START
 ↓
Load Lead
 ↓
Load Transcript
 ↓
Find check version valid for call date
 ↓
For each check:
      ↓
      evaluate
      ↓
      save evidence
 ↓
Calculate result
 ↓
Gate Decision
 ↓
PASS / HOLD / QA
```

# 12. Versioning is a sneaky-important requirement

The brief says:

> Every check must use the check-library version that was live on the call date, not today's version. 

That means don't simply store:

```text
check = rates_check
```

Store:

```text
check = rates_check
version = 3
effectiveFrom = ...
effectiveTo = ...
```

When scoring:

```javascript
findCheckVersion(callDate)
```

For example:

```text
Call date:
2026-09-10

Current rules:
v5

But v3 was active on 2026-09-10.

→ use v3
```

This is a really good thing to mention to a mentor because it shows you understood the regulatory/audit side.

# 18. 5% human sampling

This is another requirement that you can easily overlook.

Even clean calls should be sampled:

```text
95% → normal flow
5%  → human QA sampling
```

The purpose isn't to punish anyone.

The brief says this is used to measure model calibration and auditor consistency. 

For the hackathon, you don't need to build a sophisticated random sampling platform.

You can implement:

```javascript
Math.random() < 0.05
```

and route those calls to:

```text
HUMAN_SAMPLE
```

But for reproducibility in the demo, I'd actually implement a deterministic demo mode too.

# 41. If mentor comes to YOU asking "What are you building?"

Have this answer ready.

I’m building an automated QA gate for sales calls.

The flow is: recording and Lead ID come into the system, the transcript is associated with the lead, and then we evaluate the call against the retailer’s versioned checklist.

I’m handling the three check categories separately: verbatim/script checks, factual checks against CRM and retailer data, and behavioural checks.

For every result I’m storing the decision, confidence, transcript evidence, timestamp, and check version so the result is explainable.

Then a gate decides whether the sale is auto-approved, held for the TL, or routed to QA when confidence is low.

I’m deliberately using deterministic logic where possible for factual checks and AI mainly for semantic or behavioural evaluation.

That answer makes it immediately clear that you understand the problem rather than just "I made an AI chatbot."

# 42. If the mentor asks "Why not use an LLM for everything?"

Give this answer:

Because the system is making a business-critical gate decision.

For deterministic information like rates, email, dates, CRM values, and exact required scripts, I want predictable and auditable rules.

I use an AI model where semantic interpretation is actually needed, especially behaviour checks and ambiguous language.

That also makes it easier to explain failures and control false-passes on critical checks.

# 43. If they ask "What happens when the AI isn't sure?"

Your answer:

We don't auto-pass uncertainty.

A low-confidence result goes to human QA. A critical failure holds the sale, and the reviewer gets the exact evidence and timestamp needed to investigate it.

The principle is that uncertainty should be visible rather than silently converted into a pass.

That lines up directly with the gate requirement.
